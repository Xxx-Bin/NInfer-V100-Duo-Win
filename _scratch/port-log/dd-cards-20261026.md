## C1 · prefill 大消息 collective（D1 线索）— 出队

**① 流量守恒（kill 的机制面）。** TP2 下 RS+AG 与 one-shot 每 rank 总流量同为 2M（RS: 收发 M/2×2；AG 同；one-shot: 发 M 收 M）。
上游 D1 的 +34.2% 在 TP4 才有流量差支撑：one-shot 每 rank 3 发 3 收（6M）vs RS+AG 环（3M）——**TP4 上是一半流量差，TP2 上是零**。
`inventory-retained.md` D1 行自己标注 **TP4 专属**；+34.2% 是顺序阶梯值（可信度再打 ×0.41~0.45）。
本机收益只能来自重叠/流水，与拓扑（NVLink 6 链路 vs PCIe x4）无关——2-rank 流量守恒不因链路类型改变。

**② fork 现状（kill 的占比面）。** prefill 大消息（26MB）> `kPacketMaxBytes`（80KB）> `kDirectAllreduceMaxElements`（256KB），
走 copy route（`allreduce.cu:665-691`：event A → 双向 pull B → residual_add C，三相位 event 串行）。
每 chunk collective 数为层深量级（每层 GDN output + MLP down，attention 层再加 o_proj，合计 ~100 次/chunk），
pull 流量 ≈ 100 × 26MB ≈ 2.6GB/rank/chunk。

**③ 占比双界。**
- 经验上界：mixer-survey 三大块（3.02+0.99+4.28=8.29s）之外余量 ≈ **0.10s / 8.39s ≈ 1.2%**（含 collective+norm+杂项）。
- 带宽下推：2.6GB @ 保守 25GB/s（copy route 有 event 串行，实际远低于 NVLink 峰值）→ ≤116ms ≈ **1.4%**；现实 50~100GB/s → 0.3~0.7%。

两界都低于 kill 线 5% 约 4 倍。即使 RS+AG+完美重叠，可省上限 = 整个 collective 时间 ≈ ≤1.4% prefill，也低于 1% 红线的立项可行性（工程 = 新 collective + 协议 + graph capture 兼容）。

→ **出队，不进快速验证。**

## C2 · GEMM 融合反量化 — 出队

**现状核实**（`nvfp4_cutlass_sm70.cu`）：只有 CUTLASS 路线（wide-T down 投影 plain rank，T≥33）先物化：
dequant kernel 写 `w_fp16`（down：5120×8704 fp16 ≈ 85MB）+ `bf16_to_fp16_kernel` 转换 x（≈89MB 读写），再进 GEMM。
**gate_up 与其余 wide-T GEMM 走 QPN mma kernel（`nvfp4_volta_qpn_gemm.cuh`），解码在寄存器 inline 完成，本就无物化——没有油水。**

**省量口径（每层每 rank，down 投影）：**
- 物化 write 85MB + GEMM 侧 w_fp16 读改读 codes/scales 净省 ~61MB + x 转换省 ~89MB ≈ **235MB/调用**
- @900GB/s ≈ 0.26ms/调用；× 层深（~50 层量级）≈ 13ms/chunk ≈ **0.15% prefill**（@500GB/s 也只 0.23%）

**原 "~5% prefill 上限" 是量级误读**："GEMM 时间的 ~7%" 把 60% MFU 的 compute-bound GEMM 当分母直接换算到 prefill，
而 dequant/转换 kernel 是 0.1~0.3ms 量级的 memory-bound 小核，实际占比被高估 ~30 倍。

**融合代价**：CUTLASS sm70 自定义 LoadIterator + BlockScaleK16M128x4 非仿射 scale 平面，寄存器压力真实存在；
收益低于 MDD 0.481%（做了也测不出）。变通方案"加载时预物化 w_fp16"需 4.3GB/rank，显存放不下，否决。

→ **出队。**

## C3 · GDN chunked 复活三条路 — 立项条件成立（W 指数分布统计已出，2026-10-26 06:5x）

**① 方向正确性。** S4 根因是仿真层（bf16→4×f16 展开、tf32→3×f16+24shfl、ldmatrix→逐 lane LDS.32），三条复活路全部直指仿真层。

**② 关键机制澄清（本次尽调的核心产出）。** Volta f16 mma 与 tf32 **同为 10 位尾数**——3×f16 拆分的动机是
**fp16 指数域太窄（5 位 vs tf32 的 8 位），不是精度**。因此：若 K/W 能用 **2 的幂**预缩放进 fp16 指数域
（2 的幂乘法对浮点是精确操作，不引入新舍入），单次 f16 mma 即达 tf32 等价精度 → state_passing 的
3× 展开与 shfl 全部消失，"state 可能砍半"（§6 原话）从猜测变成机制上成立。

**③ 静态性核查（kill 条件的正面回答）。**
- K 侧：已 L2 归一化（|k|≤1，S3 已证）→ 静态预缩放无障碍。
- W 侧：T_inv / state 递推矩阵动态范围可达 ±30（S3 调试记录）→ **fp16 指数域大概率装得下**（30 << 65504），
  但下界（次正规区）与分布尾部需实测。**需要一次 W/T_inv 指数分布统计**：
  用 lab 分支 `port/gdn-chunked-s1` 现成 harness（`_scratch/validate_gdn_pipeline.cu`），加打印跑一次，
  半小时级，**不占 measure 轮次**。
- 若确需 per-chunk 动态缩放：device-side max-reduce（小 kernel + device 标量，**无 host sync**）可兜底，
  代价 = 一次小 launch + 精度边界重验（oracle 转 B 类，判据用 queue-v2 裁决 #1 三段式）。

**④ 收益折算（乐观/保守两档）。** state 2.90→~1.0-1.5ms、prepare 2.54→~1.3ms、LDS.64/128 省 0.3-0.5ms
→ chunked 7.57→~4.4-4.7ms/调用 < recurrent 5.33ms（**−42% 大概率翻正**，kill 条件不命中）。
按 S4 实测比例（+2.24ms/调用 ↔ −24.2% prefill，≈10.8%/ms 线性映射，单样本折算）：
- 三路全落地（净省 ~0.7-0.9ms/调用）→ **+7~10% prefill**
- 打对折（只落地两条）→ ~+4% prefill

均远过 1% 红线。风险：3-5 天工程量、B 类 oracle（acceptance 漂移）、W 求逆数值稳定重验。

→ **不立项也不封存。下一步 = W 指数分布统计（半小时级），结果决定立项或永久封存。**

**⑤ W 指数分布统计结果（2026-10-26，`port/gdn-chunked-s1` @ `de76e0b2`，`_scratch/gdn_w_stats.{cu,log}`）。**
纯 host 复刻 validate_gdn_pipeline.cu 的 fp64 oracle（k L2 归一化 bf16、64-token Wy chunk、T_inv 下三角递推），
kT=512（8 chunk），16 seeds × 8 配置（base / corr / mild / alt 相关强度 0.50→0.99 梯度）：

| 操作数 | max | minNZ | span (bits) | 静态 scale | 缩放后 | subnormal 占比 |
|---|---|---|---|---|---|---|
| T_inv | 1.0 | 1e-7~9e-10 | 22~30 | 2^14 | ≤1.6e4 | 0.07~6.8%① |
| W | 0.16~0.23 | 3e-9~2e-8 | 21~26 | 2^16~17 | ≤3.0e4 | 0.06~0.7%① |

① subnormal 只出现在 alt.99 病态配置（Af=±0.996 交替），对应 (1−c)^d 深衰减项，量级 ≤1e-9，贡献可忽略。
其余全部配置 subnormal ≤0.35%。fp16 normal 域 span = 29 bits（2^−14~2^15），**所有配置留 3~8 bits 余量**。

**机制澄清（梯度扫的意外产出）**：交替符号强相关（Af=±c）下 T_inv 按 (1−c)^d **衰减**（max 恒为 1.0），
增长机制需要真实数据特有的部分聚类结构——S3 真实记录 |T_inv|≈30 仅比 1 高 ~4.9 bits，
按 minNZ~1e-6 折算 span ~25 bits，静态 2^10 缩放后 [~1e-3, 3.1e4]，仍在域内。

**裁决**：kill 条件不命中——K/W 静态预缩放（2 的幂，指数域精确操作）在全部忠实配置下成立，
无需 per-chunk 动态缩放、无 host sync。三路合计收益估计维持 +4~10% prefill（乐观/保守两档）。
**C3 立项**。风险面不变：3-5 天工程量、B 类 oracle（acceptance 三段式）、W 求逆数值稳定重验；
补充风险：合成输入未复现真实 T_inv 增长结构，**立项后第一个动作应是拿真实 prefill chunk 的
W/T_inv 实测分布复核本表**（lab harness 挂 workspace dump，一次推理即可）。

## C4 · Streaming/Fp32Scale — 出队

**上游源码确认**（`nvfp4_volta_qpn_gemm.cuh:294-471`，prepacked kernel 模板参数）：
- `Fp32Scale`：weight divisor 不再折进每 group scale 的 fp16 乘法（fork 现状 `sc2 = __hmul2(decode_scale, divisor2)`），
  改为解码时只乘 group scale、**在 epilogue 用 fp32 乘 `256×inv_divisor`**。舍入点全变 → mma 输入逐位不同 →
  **纯精度路径改动**，本项目 A 类 oracle（sha1 `06287348665d3648`）必变，B 类三段式判据下 decode 数值路径全变、
  acceptance 漂移风险不可控 → 触发 kill"改 oracle 类"。
- `Streaming`：权重码/scale 用 `__ldcs`（流式驱逐策略）替代 `__ldg`。唯一吞吐机制 = 缓存策略；
  但 fork decode GEMV 带宽利用率仅 ~38%、延迟受限（inventory 第 4 行口径），砍流量不换时间。
  上游 B10 名义 +0.42% × 0.45 ≈ **+0.19% < MDD 0.433%**。
- `GroupUnroll`：纯调度旋钮，随 PairedProjection 附带，无独立收益主张。
- 上游文档 B1 是阶梯**起点**（157.312，无 Δ）——它本身没有被声称过收益。

→ **出队（双 kill 条件均命中）。**

## C5 · vector16 SASS 探针 — 永久结案

- 尽调已完成（STATE.md 第 2/3 节）：key_split 是 8 维/lane、stride 2048B，16B 需邻 lane 拼段。
- **探针已实现并编译**（基 `f9e5ce82`，diff 存档 `_scratch/port-log/c5-vec16-probe.diff`）：
  fast-path 改 16B 对齐 int4 加载（偶 lane 低半 / 奇 lane 高半，语义等价 A 类；顶 lane 越界回退 int2）。
- **SASS 判决（基线 vs 探针，同一 24 个 key_split 实例化）：**
  - 基线（build-v2，f9e5ce82 未改）：`LDG.E.64.SYS` 1536（=24×64），**0 条 128**。
  - 探针：`LDG.E.64.SYS` 2304（=24×96），**0 条 128** —— 每实例化恰好多 32 条 64 位，
    即 32 个 int4 全部被 ptxas 拆成 2×64 位（无法证明运行时偏移的 16B 对齐，保守拆分）。
  - 工具链本身能出 128：同二进制其他 kernel 共 46,449 条 `LDG.E.128`（基线 31,432），排除环境因素。
  - 注：压缩前一度报“探针段 17 条 LDG.E.128”系分段计数错误，文件级重扫已否定。
- **结论：编译器不会为运行时偏移的 int8 指针发 128 位加载；强制对齐需 inline PTX/`__align` 陷阱类改动，
  按 kill 条件“无 `LDG.E.128` → 永久结案”执行，不占测量轮次。**
- 现场已还原：探针 diff 存档后 revert，worktree 回 `port/packet-allreduce`，临时分支已删。
  原始 SASS dump（probe 4.1GB / baseline 3.3GB，UTF-16）已删，可用
  `_toolchain/downloads/cuda_cuobjdump-windows-x86_64-12.8.90-archive/bin/cuobjdump.exe -sass <exe>` 重新生成。

## #7 · projection epilogue publish — 维持否决

- **prefill 侧（宽 T）**：消费端是 copy-route collective（26MB）。epilogue publish 需 GEMM CTA 直接 st.global 写
  peer 的 26MB staging（双缓冲）；省掉的是 phase B pull ≈ 26MB @ 50~100GB/s ≈ 0.3-0.5ms × ~100 次/chunk
  ≈ **0.4~0.7% prefill < 1% 红线** → prefill 侧不成立。
- **decode 侧**：折算 +0.64~0.70% 贴 MDD 0.433%，余量薄；最贵工程（改 CUTLASS/QPN epilogue + 协议 + graph capture）。
  rmsnorm-wiring 的 −2.748% 虽机制不同（publish 在 GEMM epilogue 侧、CTA 多，几何上比 collective 内做 norm 好），
  但它是同几何下"往窄 T collective 路径加 publish/spin 开销"的实测负例——风险不对称。
- HANDOFF 要求"证明 prefill 宽 T 几何不受 rmsnorm 退化影响才可复活"：几何上确实不同（publish 不动归约结构），
  **但即便成立，收益也过不了 1% prefill 红线** → 推翻否决的理由不存在了，维持否决。

→ **维持否决。**
