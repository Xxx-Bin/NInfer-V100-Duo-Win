## 五、跑完怎么办（判定树，事先定好）

### 每一步都一样的三段判定

1. **oracle 先看**
   - A 类（逐位一致）→ 继续看性能
   - B 类 → 过三段式（acc/drf/rd 严格相等 + alen/per-pos 相等 + ID 差异 ≤2%），否则否决
   - FAIL → 功能错，修或弃，不看性能
2. **性能对冻结预测**
   - **≥ 门槛（+0.5%）** → 打 `result/<feat>`，进"保留候选"，等联合裁决
   - **介于 噪声地板 与 门槛 之间** → 记录为"已达判据上限但未过门槛"，**存档，不反复重测**。  
     这类项一律进最终联合裁决，由裁决统一决定去留，不允许"多跑几次碰运气"
   - **< 噪声地板** → 说明**预测模型错了**（不是"收益小"）。必须回头修正机制理解，  
     并检查是不是像站点 A 那样把 kernel 内部并行度改坏了
3. **无论结果**：写 `port-log/<feat>.md`（含 oracle 类别、两 rep 原始值、判定、失败机制），  
   commit + tag，**保留 lab worktree**。

### 全部跑完之后的联合裁决

单看每项都过门槛，不等于叠加起来仍过门槛（站点 A 与 packet 共享同一套邮箱协议，互相影响）。  
最终需要**一次联合测量**：把保留候选合到一个分支上测一次，并检查：

- 每项的目标指标是否仍达标
- 非目标指标是否回退超过噪声
- 是否出现协议冲突（如两种 packet 变体交替使用同一组 epoch 计数器）
