# 实测噪声地板（2026-10-25）

目的：把"这个协议到底能分辨多大的差异"从猜测变成常数，写进 `judge.py`
（`NOISE_RUN_SD_PCT` + `mdd_pct()`），以后每次判定自动带可分辨性结论。

## 方法

**同一个二进制**（`result/packet-allreduce` = `df1f2958`，lab worktree 检出该 tag 重建）
连续跑 4 次测量。每次测量内是 `warmup=1 + reps=2`，即 4 次运行 / 8 个 decode 与 prefill 样本。
每次测量前确认 GPU 空载（10 MiB）、测量窗口内不派任何代理、不编译。

这是**纯噪声**测量：被测代码与参照完全相同，任何非零差都是噪声。

## 原始数据

| 运行 | prefill rep0 / rep1 | decode rep0 / rep1 |
|---|---|---|
| `packet-allreduce` | 946.50 / 944.74 | 135.4398 / 135.7477 |
| `noisefloor-r1` | 947.87 / 945.54 | 135.8052 / 135.8626 |
| `noisefloor-r2` | 946.35 / 945.37 | 135.7755 / 135.7897 |
| `noisefloor-r3` | 943.38 / 942.58 | 135.7792 / 134.9771 |

## 统计

| 指标 | 全体样本 sd | 各次运行均值的 sd | 运行间极差 |
|---|---:|---:|---:|
| decode | 0.221% | **0.153%** | 0.336% |
| prefill | 0.181% | **0.170%** | 0.394% |

去掉唯一离群样本（`134.9771`）后，decode 全体 sd 降到 0.102%。

## 两个结论

### 1. 噪声几乎全部来自"运行之间"，不是 rep 之间

一次运行内的两 rep 只差 **0.01~0.06%**；跨运行却差到 0.15%（sd）、0.34%（极差）。
说明波动源是每次进程启动后的初始状态（模型加载、显存布局、时钟），**不是测量过程本身**。

→ 推论：**增加 reps 对降低噪声帮助有限**，增加**运行次数**才有效。这与"多跑几 rep 更准"的直觉相反。

### 2. 最小可分辨差异（MDD，95%）

A/B 两次独立测量的差值标准差 = `sd × √2`，95% 取 2 倍：

| 比较方式 | decode | prefill |
|---|---:|---:|
| 单次运行 vs 基线（2 reps） | **0.433%** | 0.481% |
| 两次运行取均值（4 reps） | 0.306% | 0.340% |
| 三次运行取均值（6 reps） | 0.250% | 0.278% |

## 对既有结论的重新解读

| 项 | 实测 delta | 与 MDD 0.433% 比 | 结论 |
|---|---:|---|---|
| packet | **+4.523%** | 远高于 | ✅ **有效，结论成立** |
| GDN split-10 | +0.369% | **低于** | ⚠️ 本来就在测不出来，不是"差一点过门槛" |
| 融合 RMSNorm | −2.748% | 远高于（负向） | ✅ 退化结论成立 |
| TileN | +0.473% | 略高于 | 勉强可分辨，但仍未达 +1.0% 门槛 |
| MTP shortlist argmax（预计） | ~0.42% | **正好在边缘** | ⚠️ 该轮无论结果如何都不能单独定罪 |

## 协议建议

1. **门槛 +0.5% 恰好等于 2-rep 协议的 MDD（0.433%）** —— 门槛设在这个位置，意味着
   "过门槛"和"测不出来"只差 0.07 个百分点。这是判据与测量能力不匹配，不是被测项的问题。
2. 建议：**凡预期 < 0.5% 的项，判定必须基于 ≥2 次运行（4 reps）**，MDD 降到 0.306%。
3. 若某项落在 MDD 与门槛之间，按 `plan-next-two-runs.md` 的处理：**存档、不重测**，
   留给最终联合裁决。
4. `judge.py` 已内置这些常数，每次运行会输出 `--- RESOLUTION ---` 段，逐指标给出
   "可分辨 / 低于可分辨下限"。**低于下限的测量不构成"有效/无效"的证据。**
